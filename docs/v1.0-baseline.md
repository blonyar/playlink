# Playlink v1.0 Baseline Goal

## 1. Product Judgment

Playlink should converge on a stable baseline for small room-based multiplayer before adding heavier networking modules.

The v1.0 target is a modular multiplayer networking toolkit for 2-8 player games, prototypes, LAN parties, and room-based online play. The first stable contract is not a full backend platform. It is:

```text
JSON/WebSocket room protocol
+ JavaScript helper API
+ dev-only debug console
+ example-led state sync convention
+ one-command verification flow
```

This baseline should make the current working loop dependable enough that future modules can be added without rewriting the room core.

## 2. Stable Baseline Contracts

### JSON/WebSocket Room Protocol

The v1.0 protocol baseline is the message set documented in `docs/protocol.md`:

- client messages: `create_room`, `join_room`, `leave_room`, `room_message`, `ping`
- server messages: `room_created`, `room_joined`, `room_left`, `player_joined`, `player_left`, `room_broadcast`, `event_lagged`, `pong`, `error`
- structured error codes documented in `docs/protocol.md`
- request/response correlation through optional `id`
- one active room per WebSocket session
- empty-room cleanup after the last player leaves or disconnects

Future protocol changes should be additive unless a new major baseline explicitly breaks the contract.

### JavaScript Helper API

The v1.0 helper baseline is the example API documented in `docs/js-client-api.md`:

- `PlaylinkClient`
- `createStateSnapshot`
- `StateSnapshotFilter`
- `StateSnapshotPublisher`

The helper remains an example-local module, not a published npm package. Breaking internal helper structure is allowed, but documented methods, options, emitted protocol shapes, and error behavior should remain stable for v1.0 examples.

### Debug Console Boundary

The Web Debug Console is a development and inspection surface. It may show server health, metadata, stats, rooms, players, and raw messages.

It is not a production admin product. v1.0 should not add accounts, operator roles, production permissions, audit trails, or remote administration workflows.

### State Sync Example Contract

The v1.0 state sync baseline is a convention inside `room_message.payload.data`, not a new core protocol feature:

```json
{
  "kind": "state_snapshot",
  "tick": 123,
  "entity_id": "player-id",
  "state": {
    "x": 54,
    "y": 50
  }
}
```

Rules:

- `tick` is a non-negative safe integer and monotonic per `entity_id`.
- `entity_id` is a non-empty game/example-owned string.
- `state` is a JSON object owned by the game/example.
- receivers reject duplicate, stale, or out-of-order ticks per entity.
- the server treats state snapshots as ordinary room messages.

This is not server-authoritative validation, physics replication, rollback, ECS replication, or a generic game-state engine.

### Verification Flow

The v1.0 baseline gate is:

```powershell
.\scripts\verify.ps1
```

That command must continue to cover:

- Rust formatting, compile checks, and unit tests.
- JavaScript syntax checks.
- state snapshot helper checks.
- server-backed smoke, error, and SDK demo scripts.

Manual browser checks remain acceptable for visual mini-game behavior until a browser test harness exists.

## 3. Real Constraints

- The room protocol is a user-facing contract.
- The JavaScript helper API is an example-facing contract.
- Raw WebSocket + JSON must remain usable without the helper.
- Room/session cleanup must be idempotent for explicit leave, disconnect cleanup, and idle timeout paths.
- The debug console must remain useful without becoming a production admin system.
- State sync must stay example-led until multiple real examples prove the need for core protocol changes.

## 4. Inertia Constraints

- Current milestone numbering is not a product contract.
- Current branch naming does not define the product stage.
- Internal Rust module boundaries are not public compatibility obligations.
- Backward compatibility is not required for undocumented helper internals.
- Single-crate structure should remain until module boundaries are stable enough to justify splitting.

## 5. Explicit Non-Goals

Do not add these to reach v1.0:

- accounts
- databases
- global matchmaking
- anti-cheat
- production admin permissions
- server-authoritative simulation
- ECS replication
- rollback netcode
- premature crate splitting
- compatibility shims for undocumented internal APIs

## 6. Migration And Cleanup Path

1. Mark v0.9 lightweight state sync prototype as complete wherever current code and docs already prove it.
2. Remove stale language that says v0.9 is still the next planned milestone.
3. Point README, `docs/goal.md`, and roadmap language at this v1.0 baseline.
4. Keep `docs/protocol.md`, `docs/js-client-api.md`, `docs/sync-models.md`, and runnable examples aligned with the same contract.
5. Add focused tests when a baseline invariant is not directly covered.
6. Run `.\scripts\verify.ps1` before calling the baseline healthy.

## 7. Acceptance Criteria

v1.0 baseline work is complete when:

- [x] README status table says v0.9 is complete and v1.0 baseline is the active convergence target.
- [x] `docs/goal.md` names v1.0 baseline as the next milestone.
- [x] `docs/protocol.md` documents the frozen JSON/WebSocket room protocol contract.
- [x] `docs/js-client-api.md` documents the helper API baseline.
- [x] `docs/sync-models.md` describes v0.9 as implemented and keeps server-authoritative sync out of scope.
- [x] cleanup idempotency is covered by a Rust test or integration script.
- [x] stale/out-of-order state snapshot filtering is covered by a JavaScript helper check.
- [x] `.\scripts\verify.ps1` passes.

## 8. Push Beyond v1.0 Only If

Future relay, P2P, additional SDKs, or server-authoritative experiments should wait until the baseline above is true and verified.

The baseline should be reopened only if concrete evidence shows the current contract is insufficient, such as:

- at least two examples need a server field that cannot be added compatibly.
- state snapshot conventions cannot express common small-game movement without core support.
- debug workflows require data unavailable through current health, stats, server metadata, or room APIs.
- integration scripts pass while a documented protocol contract is broken.
